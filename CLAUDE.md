## Forge-specific rules

- **Changelog fragments (dogfood, since #229)**: forge uses `[tool.forge.changelog].mode = "fragments"` conventions — a PR's changelog entry is a `changelog.d/<slug>.<type>.md` file (first line `bump: patch|minor|major`, level ONLY — never a version number), NOT a `CHANGELOG.md` edit. CHANGELOG.md is assembled at release (`forge-changelog assemble`); nothing reads it as a version signal. Versions are assembler-owned: PRs never bump `plugin.json` (it parks at the latest tag; the guard accepts that with valid pending fragments) — a release PR runs `forge-changelog release`, which computes the version from the pending fragments' max level and is the manifest's single writer.

- **Version derivation**: pip package version comes from the latest git tag via setuptools-scm. There is no manual `version = "x.y.z"` in `pyproject.toml`. Release flow: `git tag vX.Y.Z && git push origin vX.Y.Z`.
- **PR & branch granularity — bundle cohesive work, don't reflex-split.** A PR is the smallest *cohesive* unit, not the smallest possible one. In forge every PR also costs a rolling-next `plugin.json` bump + a tag on merge, so splitting *related* changes across PRs multiplies that ceremony to buy isolation nobody needs. **Default to ONE PR** when the changes share a subsystem, must land together, or one half is meaningless without the other — e.g. a bug a type checker surfaces *while you build the feature that runs it* belongs in that feature's PR, not a parallel one; a follow-up cleanup to code this PR introduces belongs here too. **Split only for a concrete reason:** independent risk/rollback, different reviewers or release cadence, a hard blocking dependency, or a diff too large to review in one sitting. "It's a separate concern" does **not** justify a separate PR when the concerns ship together — separateness of *topic* ≠ separateness of *delivery*. When unsure, bundle. (File a separate *issue* freely for deferred work — that's cheap; it's separate *PRs/branches* that add the burden.)
- **Release process — SINGLE-TRACK**: specified in **[`docs/release-process.md`](docs/release-process.md)**, the single source of truth + the **invariant→test contract**. Do not restate its mechanics elsewhere; point here. Operational summary:
  - Every PR targets `main`; every merge tags. `.claude-plugin/plugin.json["version"]` is **rolling-next** — always names the version about to be released; `step_plugin_version` enforces `plugin.json > latest_tag` on every commit (skipped when `HEAD` reproduces a tagged release's tree). After a tag lands, the next PR must bump it.
  - The `tag-main` job in `tag-release.yml` cuts the tag automatically after CI succeeds on the merge; `forge-next-prep --tag` is the idempotent manual fallback.
  - The dual-track dev/main model is retired and its machinery deleted. The `dev` branch no longer exists — never target it.
  - **Every versioning invariant names an enforcing test in the spec.** Do NOT change that code without the matching spec test staying green.
- **Semver policy for the plugin bump** — when the post-tag rolling-next bump PR lands (see [`docs/release-process.md`](docs/release-process.md) §1), choose the increment deliberately, not reflexively. The plugin's public surface is: every CLI in `[project.scripts]`, every agent name + canonical Output shape under `agents/`, every Claude Code hook under `claude-hooks/`, every skill under `skills/`, every FOUNDATION rule a consumer can rely on, and the documented public Python import surface (the table in [`docs/consumer-release.md`](docs/consumer-release.md) — breaking one of those signatures is MAJOR; everything else in `src/forge/` is internal).
  - **The decision procedure is the shared one** in [`docs/consumer-release.md`](docs/consumer-release.md) "Choosing the bump" (the new-capability-vs-new-option axis). Do not restate it here — this bullet only maps the axis onto forge's plugin surface.
  - **Forge-specific applications**: a new agent / hook / skill / pre-commit step (self-skips when not opted in — a new *check* is a new capability), a new mandatory step added to an already-shipped skill, or a new non-breaking mandatory rule in FOUNDATION / `_TEMPLATE.md` → MINOR. An agent Output shape changed so existing parsers break (e.g. `pr-manager`), a hook's semantics inverted (allow → block), a FOUNDATION rule promoted from soft to blocking, a manifest layout change, or any upgrade needing action beyond `forge-upgrade` → MAJOR. CLAUDE.md edits affecting only forge contributors, and new non-blocking audit checks → PATCH.
- **`dev/` is forge-only — `./dev/setup.sh` is the ONLY install/refresh command**: `dev/setup.sh` (conda env, editable install, `install-forge-bootstrap`, doctor) is forge's own bootstrap and is **re-run safe (idempotent)**. **To refresh the editable install — e.g. to pick up a new `[project.scripts]` CLI / entry point after pulling a PR — re-run `./dev/setup.sh`.** **NEVER tell the user to run (or run) a raw `pip install`** — per FOUNDATION §2 the *exact command* for forge is this bootstrap script, not bare pip. (To automate the refresh after every pull, drop a script that runs `./dev/setup.sh` into `.githooks/post-merge.d/` — the consumer extension point added in #10.) Not a consumer pattern; consumers use whatever Python env tool they prefer + `install-forge-githooks`.
- **Plugin layout**: `.claude-plugin/` (manifest), `agents/`, `skills/` (auto-discovered), `claude-hooks/` (referenced via `${CLAUDE_PLUGIN_ROOT}/claude-hooks/...` in `plugin.json`). Do not confuse with `.githooks/` (git hooks, separate domain).
- **Git-hook version sidecar**: the tracked `.githooks/*` wrappers are **version-free**. The forge version that last wrote them lives in the gitignored `.githooks/.forge-hook-version` sidecar, read at runtime by each hook's staleness preamble (`"$(dirname "$0")/.forge-hook-version"`). This keeps the committed hooks byte-stable across version bumps — critical here because forge is editable-installed, so `metadata.version()` returns an ever-changing `X.Y.Z.devN+g<sha>.d<date>` string that would otherwise re-stamp (and dirty) the hooks on every `post-merge`/`post-checkout` auto-refresh. `install-forge-githooks` writes the sidecar and ensures it's gitignored on every run; the marker carries only `body-sha=` (consumer-edit detection), never `forge-version=`.
- **FOUNDATION.md location**: canonical file at repo root for contributors. Shipped via pip as `src/forge/data/FOUNDATION.md` (symlink). `install-forge-claude-md` reads from `importlib.resources`.
- **`manifest_json` step** in `forge-precommit` fires here because forge ships a plugin (`.claude-plugin/` present). It self-skips in consumer repos that don't ship a plugin.
- **Step invocation architecture** — `forge-precommit --only <step>` is the single standard entry point; a step ships a standalone forge CLI only when the CLI *is* the tool or does real orchestration. Full rule, criteria, and the direct-invocation invariants (explicit `repo_root` threading, `--` argv separator, skip-before-`require_cli`) live in **[`docs/step-invocation.md`](docs/step-invocation.md)** — read it before adding or changing a pre-commit step; do not restate its mechanics elsewhere.
- **`pip_audit` step is non-blocking by default** (since v1.1.3): renders as yellow `WARN` if CVEs are found, never fails the overall pre-commit. Use `StepResult(non_blocking=True)` for any future advisory step. **Configurable since v2.3.0**: `[tool.forge.pip_audit].blocking = true` makes CVE findings a hard `FAIL` (same opt-in `_forge_step_config(...).get("blocking", False)` pattern as `typecheck`/`doctest`); a missing `pip-audit` binary always stays a non-blocking WARN (broken-install signal, not a finding). Forge keeps its own pip_audit **non-blocking** — an upstream dependency CVE (not forge's code, often unfixable same-day) should warn, not halt every commit — while running **`typecheck` blocking** (`[tool.forge.typecheck].blocking = true`): type errors are forge's own code.
- **`docstring_coverage` step is non-blocking**: mirrors the `pip_audit` pattern — `StepResult(non_blocking=True)`. See FOUNDATION §8 "Docstring coverage — three layered enforcers" for the full rationale and the `MISSING: <path>:<line>:<name>` dispatch contract with `forge:precommit-fixer`.
- **CLAUDE.md is consumer-owned** (since v1.1.3): foundation lives in `FOUNDATION.md`, included via `@FOUNDATION.md` near the top of this file. `install-forge-claude-md` only writes/updates `FOUNDATION.md` and the initial CLAUDE.md scaffold. Once scaffolded, this file is forge-developer territory.
- **Logging convention** (forge's documented equivalent of FOUNDATION §9): forge has no `common.logging` module. Forge CLIs use `from forge.git_utils import configure_cli_logging` once at module load + `logger = logging.getLogger(__name__)` for the module logger. `configure_cli_logging()` configures the root logger with `INFO` level and a bare-message formatter. Module-level `logging.getLogger(__name__)` is the deliberate pattern here, not a §9 violation — per §9's "consumer repos either adopt this module or document their own logging entry point in their CLAUDE.md".
- **CLI wiring is enforced by reachability** (`verify-forge-cli-wiring`, pre-commit step `cli_wiring`): every `[project.scripts]` entry in `pyproject.toml` must appear at least once in a wiring source — `src/forge/install_bootstrap.py` (STEPS list), `src/forge/precommit.py` (step functions), `src/forge/audit/` (audit orchestrator + steps), `.githooks/`, `claude-hooks/`, `dev/`, `agents/`, or `skills/`. The verifier greps these paths and fails the pre-commit when a script name is unreachable, excluding the CLI's own implementation file. Why: forge has many invocation paths and a new `[project.scripts]` line can land without being wired into any of them, producing an installed-but-uncalled CLI. The grep IS the contract — no metadata registry to keep in sync. If a CLI is intentionally unwired (release tooling, CI-only utility), add it to `cli_wiring_exempt.toml` at the repo root with `[exempt."<name>"] reason = "..."`; the verifier exempts it and reports stale entries when the script is later removed. The step self-skips when the consumer repo has no `[project.scripts]` table.
- **`forge-internal` issue label** (forge-only, since v2.7.1): forge is both a shipped product and its own active dev repo, so its backlog mixes two audiences. The `forge-internal` GitHub label marks issues about **forge-the-repo internals** (release tooling, `/next` and contributor workflow, `dev/setup.sh`, forge's own test suite / CI / this `CLAUDE.md`) as distinct from issues about the **shipped product surface** consumers use (the `[project.scripts]` CLIs, `agents/` / `skills/` / `claude-hooks/`, FOUNDATION rules, `install-forge-*`). It is deliberately **NOT** in the shipped `CANONICAL_LABELS` (`src/forge/install_labels.py`) / FOUNDATION §14 schema — it would be meaningless in a consumer repo (every issue there is already "their internal"), so `install-forge-labels` never creates it. Create it only on forge's own repo (`gh label create forge-internal --color 006B75 ...`). Triage awareness rides a **forge-local wrapper agent** `.claude/agents/issue-triage-forge.md` (FOUNDATION §16 Pattern A) that delegates to `forge:issue-triage` and adds the label rule + a Backlog Index `forge-internal` lane; the shipped `forge:issue-triage` agent stays generic for consumers. **Invoke the wrapper directly** (`issue-triage-forge`) when triaging in this repo — the shipped `/triage` skill routes to the generic foundation agent and does not apply the `forge-internal` rule.
- **Closed issues keep their tier labels** (forge-local override of the `forge:issue-triage` `post-pr` strip rule): the tier at close time is retrospective data (weekly summaries, throughput reviews) that stripping destroys. `post-pr` mode must not remove tier labels here; the Backlog Index lists only open issues, so closed-issue labels never pollute it.
- **`_FORGE_GITHUB_REPO` carve-out** (forge's single exception to FOUNDATION §2 "No private organizational names"): the canonical upstream constant in `src/forge/git_utils.py` (and URLs derived from it) must name the public upstream — that constant only, not "any public GitHub URL". During a repo move it stays at the *functional* location (where the gh API returns 200s) while docs may forward-point at the *aspirational* one — a bounded divergence flagged by a README callout.
- **Approved `# noqa` exceptions** (FOUNDATION §5 normally permits only `E402`):
  - `# noqa: N802` — for `ast.NodeVisitor` `visit_*` methods, stdlib forces PascalCase suffixes like `visit_FunctionDef` (e.g. `verify_docstrings.py`).
  - `# noqa: PLC0415` — for guarded optional-dependency imports under `try / except ImportError` inside a helper, where moving the import to module level would break consumers without the extra (e.g. `audit/orphans.py:78` for `vulture`). Module-level guarded imports are preferred when feasible; reserve PLC0415 for cases where the optional dep is only needed inside one function.
  - `# noqa: S105` — only for public git branch-name / commit-message marker constants whose `_TOKEN`-style name trips ruff's hardcoded-password heuristic (e.g. `NO_VERSION_BRANCH_TOKEN = "no-version"` in `changelog.py`, plus its test assertion). The value must be a documented protocol marker, never credential-shaped; any new S105 suppression outside this exact class needs fresh review. All actual secrets go in `.env` or environment variables.
