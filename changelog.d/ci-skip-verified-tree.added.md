bump: minor
- New `forge-tree-verified`: CI can stop re-running a test suite against a tree it already tested. A squash-merge rewrites the commit, its parent and its message but never the tree, so for a suite whose result depends only on the tree, the run on the merge commit repeats the run from the pull request. The CLI answers whether the tree really is identical, and the shipped CI recipe gates its test step on the answer, so a merge stops paying for a run whose result is already known.
- Whether that applies is a question about your tests, not a fact about testing. A suite that reads git history — a version derived from tag distance or commit SHA, as setuptools-scm does — or the clock, a cadence stamp, a lifecycle window or the network is not determined by the tree alone, and skipping could hide a real failure in exactly those places. The recipe says so where someone deciding will read it.
- It skips only the test execution, and only on a push whose tree matches. Everything else still runs on the default branch, pre-commit included, and the job still reports on the commit. A skip names its evidence — tree, pull request, head commit, check — so it can be re-checked by hand, and every other outcome names its reason in one line.
- Fail-closed throughout: not in CI, not a push, no merged pull request for the commit, more than one candidate, an unreachable API, a differing tree, a head that did not contain the base, a check that was skipped rather than passed, a check still running, or an anticipated fault all run the full suite. Any other exception ends the step, which the recipe's `continue-on-error` turns into a suite run rather than a failed job. A missing permission reads as `api unavailable (token/permissions?)` rather than as a silent skip.
- Two cases it refuses deliberately, because each would otherwise skip a suite that never ran: a pull-request run tests the merge of the branch with its base rather than the branch itself, so the branch must already have contained the base; and a job skipped for a bot or a draft is not a job that passed, so a named job must have concluded success.
- What it trusts is a job of the workflow asking the question, found through the Actions API, rather than a check of a given name. A check-run's name identifies nothing: anything with permission to write checks can post one under any name, a step using the built-in token posts it under GitHub's own identity, and two workflows in the same repository can share a job name by accident. Asking which run of this workflow file ran for that commit, and how its job concluded, is a question only someone who can change the workflow can answer falsely. Adopting the gate therefore needs `actions: read` in the workflow's permissions, and the recipe says what a matrix or reusable workflow does to the job's displayed name.
- Unrelated to the gate, from the same work: ruff's `T201` (bare `print`) is now marked unfixable here, because its fix deletes the statement — a new CLI's output vanished under a green lint verdict while writing this one. `docs/step-invocation.md` points CLI authors at `forge.git_utils.emit` instead.
- The saving depends on branch protection requiring branches to be up to date before merging. Without it a behind branch can be squashed, the trees differ, and the gate declines — costing a normal test run, so such a repo is unimproved rather than worse off. Note also that an identical tree is not an identical environment: a skipped run does not re-prove the suite against newer dependency releases, so `forge-precommit` keeps running on the default branch and a scheduled full run remains the way to get that signal on a timer.
