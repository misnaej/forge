bump: patch
- **A failed assembly run now files itself as an issue, and runs daily while that is proven.** The scheduled `assemble-release` workflow is what advances `.claude-plugin/plugin.json`, and Claude Code keys its plugin cache on that version — so when a scheduled run failed, the manifest stayed frozen at its last assembled version across fifteen subsequent tags, and no consumer could reach the guard hardening those tags shipped. Nothing reported the failure: GitHub mails only whoever last touched the cron, and the backlog everyone reads showed nothing. The workflow's failure path now opens an issue naming the run and the consequence, or comments on the existing one rather than filing a duplicate. The cadence moves from weekly to daily while the fix is observed, then to Mondays/Wednesdays/Fridays — a weekly schedule turns one silent failure into a week of frozen plugin distribution.
- **A declared plugin version must be one consumers can read about.** `verify-forge-plugin-version` now refuses when `.claude-plugin/plugin.json` names a version that has no matching `## v…` heading in `CHANGELOG.md`, on every path where it previously passed. The manifest version is not bookkeeping — Claude Code keys its plugin cache on it, so it is the identity consumers actually adopt, and a version with no entry is one they cannot evaluate before running it. The assembler writes the version and its heading together, so its output always satisfies this; a mismatch means the manifest was hand-edited. Note the deliberate limit: this asks whether the declared version is *real*, never whether it is *current* — a manifest parked at an older version keeps its heading and passes, because staleness is the scheduled assembly's job. Repos that ship a manifest previously had no enforcement of this at all: the changelog step self-skips whenever a manifest exists.
