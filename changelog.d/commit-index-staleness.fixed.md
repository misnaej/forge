bump: patch

- `forge-commit` no longer refuses the commit it just staged. It stages before reading the pre-commit verdict, deliberately, so a new file gets checked — but staging moves the index, and the two steps judged against the index (`regen_docs`, `changelog_updated`) then no longer described it. A verdict that passed moments earlier was refused, and the only way through was to run the whole battery again and commit a second time. It now re-runs those two steps itself and proceeds. A step that fails the re-run still refuses the commit: the outcome is read from the run's own results, because a targeted run records its markers where the verdict does not look.
- One of those steps regenerates rather than checks. When the re-run rewrites a generated doc, `forge-commit` says so and still refuses, naming the file it staged — the regeneration belongs in the commit, but it moved the tree, so every step is owed a full run. A retry is no longer refused over a generated doc that forge itself left staged.
- A failed verdict caused by a moved index now says so, and says what to do: it names the index-reading steps and the `forge-precommit --only` that refreshes them, instead of advising a full run that the unchanged working tree does not need. Every other cause keeps its wording, and a failing or missing step outranks this one — "re-run these two" must never be the advice while a failure goes unnamed.
- A refusal from `forge-commit` shows every row that explains it. It previously printed the last six lines of the verdict, which on a long run were all `PASS` rows, so the cause line named steps whose `STALE` rows had scrolled out of the message.
