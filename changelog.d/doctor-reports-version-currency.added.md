bump: minor
- **The health check now says when forge itself is out of date, not just when its pieces disagree with each other.** It already compared the installed package against the git hooks and reported them aligned — which they can be while both are equally old. That is what happened: it reported alignment at one version while the checkout had already moved a release ahead, so the reassuring line was true about agreement and silent about being current. It now also reports an installed build that is behind the newest release its own checkout is built on, naming both versions and the command that refreshes it.
- **Why a build goes stale at all**, since the report now explains it: the version is worked out when the package is installed, and a release cut afterwards is not picked up until the next install. Right after a merge, that is every checkout.
- Only forge's own working copy is judged this way. In a project that merely uses forge, the newest tag is that project's own version and has nothing to say about which forge is installed, so no comparison is made.
- **One rule now decides which forge build is newer, everywhere that asks.** A development build counts as preceding the release it anticipates rather than matching it — which is what being exactly one patch behind looks like, and was previously invisible. Five places ask that question and four of them answered it the blind way, so four reports change, all of them in the same direction and all naming the same fixes they always did:
  - The comparison between the installed package and the git hooks now reports one as behind the other where it used to call them level.
  - The commit-time gate on the git hooks now blocks that case instead of allowing it.
  - The notice that a newer forge is available now appears for a checkout one patch behind, where it used to stay silent.
  - The count of upgrade steps still owed no longer skips the steps belonging to the release a development build is on its way to.
