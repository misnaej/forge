bump: minor

- **A validated plan can no longer run on a premise the code has since outgrown, and unfinished work no longer unblocks what depends on it.** A plan approved for unattended work used to be checked against the code only by a judgment "spot-check", and a prerequisite counted as done the moment its issue closed, even when its work never merged. A new `forge-plan-check` command makes three checks mechanical: `prerequisites <issue>` passes only when every `Requires:` entry's work merged (an issue closed as not planned, or by hand, still blocks); `drift <issue>` lists merges since the plan's approval that touched the files it names (a merge that delivers the issue's own prerequisite is noted, not counted), and refuses an issue labelled both `blocked` and `plan-ready`; `overlap <pr>` lists the open issues naming a file a merged PR changed. Each exits 0 clean, 1 finding, 2 unknown — a GitHub failure is never read as clean, and a plan comment counts only from an author with write access. `/sentinel` runs `drift` and `prerequisites` at pickup and skips on any finding; `issue-triage`'s `post-pr` mode moves overlapping `plan-ready` issues to a new `needs-recheck` label; `/plan-issue` shows what changed since the issue was filed; `/next` and plan-readiness screening use `prerequisites`. FOUNDATION §14 states the rules: `blocked` and `plan-ready` never coexist, and a prerequisite means the work landed. `gh_comments.parse_paged_json` gains a `strict` mode that raises instead of skipping a bad page.
