bump: minor
- **A merge that ships without a release tag of its own is now reported instead of passing unnoticed.** Every merge is supposed to cut a release tag, computed from the changelog entries that merge brought. Several things can stop that — the tag push being refused, the job never firing, tests going red, a runner dying — and when it happens the next merge quietly counts the orphaned entries into its own tag. The version stays correct, so nothing looks wrong; what is lost is that one merge has no release naming it, and the following release notes cover two merges' work. `forge-changelog tag-gaps` reads the repository history and says so, checking the merge at hand by default or any span of history on request. The tagging job now runs it after every merge, including merges where the tagging step itself failed, so the report does not depend on the thing that broke.
- **A refused tag push now explains itself.** A remote can refuse to accept a tag whose commit holds a different copy of the automation's own workflow files than the current branch does — which happens whenever a later merge edits one of them. The refusal used to be reported as a push that failed for no discoverable reason, sending the reader to look for a race between two runners that never happened. It now names the cause, says that this merge has no tag yet and how to get one, and names the one credential change that removes the refusal.
