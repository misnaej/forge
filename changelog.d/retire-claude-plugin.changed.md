bump: major
- **The Claude Code plugin is gone. Forge's agents, skills and guards are now generated into your repo**, the same way the Mistral Vibe integration already was. `install-forge-claude` writes them into `.claude/` — agents, skills, the guard scripts, their registration in `.claude/settings.json`, and a `.claude/.gitignore` naming which files are forge's. The bootstrap runs it, and the managed `post-merge` / `post-checkout` hooks re-run it, so the version you have installed is the version you run. There is no marketplace, no per-checkout install, and no cache that can go stale. **Action required:** uninstall the old plugin once — `claude plugin uninstall forge@forge --scope user`, plus `--scope local` in any checkout that had its own — then run `install-forge-claude` and restart the session. It clears the settings keys that named the plugin. Retired with it: `forge-plugin-sync`, `install-forge-claude-settings`, `verify-forge-manifest`, the `plugin_sync` and `manifest_json` pre-commit steps, the `[tool.forge.plugin_sync]` config table, and `forge-doctor --plugin-name`. Any CI step or config of yours that names one of these breaks until it is removed.
- **Agents and skills are now named with a `forge-` prefix, which renames what you type.** `forge:design-checker` becomes `forge-design-checker`, and the slash commands move with it: `/pr` is now `/forge-pr`, `/commit` is `/forge-commit`, `/next` is `/forge-next`, and so on for every shipped skill. The prefix is part of the generated file name, so forge's agents are distinguishable from yours on sight and cannot collide with them. The same names are used on every harness, so one reference works wherever it is read. **Action required:** rename the references you own — `forge:<x>` to `forge-<x>` in your own wrapper agents, in `Task(subagent_type=...)` and `Skill(skill=...)` calls, and in your `CLAUDE.md`, docs and scripts; use `/forge-<skill>` where you used `/<skill>`; and rename any file of your own that starts with `forge-`, since that prefix is now forge's. Your unprefixed agents and skills need no change and will no longer collide with a shipped name.
- **Installing forge from a tag could fail and leave a repo with no forge at all.** The shipped agent, skill and guard sources were symlinks into the repository root, and git tracks a directory symlink as a file: the generated source manifest listed it as a file to ship, and the build then tried to copy a directory, aborting with `can't copy '<path>': doesn't exist or not a regular file`. Because the old version is removed before the new one is built, an upgrade that hit this left nothing installed — in a repository whose commit path needs forge to run. The sources are now real directories inside the package, so nothing there is a symlink and no manifest can describe one. Reported by a consumer who hit it moving a pin, and reproduced here before the fix.
- **A release tag is cut on every merge**, computed from the changelog fragments that merge brought, and the tag is the only place a version lives. Nothing in the tree declares one, so two copies can no longer disagree — the failure this replaces stranded a release that was assembled but never tagged, then produced a version that moved *backwards* while passing every check. `CHANGELOG.md` prose is assembled afterwards by a scheduled pull request, filing each fragment under the tag that already shipped it. **Action required for a consumer who wants tags cut this way:** set `[tool.forge.release].auto = "merge"`; without it the tag job warns and cuts nothing. Retired with it: rolling-next versioning, the `plugin_version` guard, `forge-rebump`, and `forge-next-prep --tag`.
- `forge-doctor` reports one `claude:integration` line — current, drifted with the files named, or not generated — in place of the three plugin-install checks.
- **Everything forge ships now counts as high-blast-radius for PR verification.** Moving the shipped sources into the package meant a pull request editing a shipped agent or skill prompt was classified as documentation-only, which skips the design and security reviewers, and a small follow-up edit to any shipped file — guard scripts included — took the abbreviated delta re-check instead of a full one. Both are closed: the whole packaged-data directory is treated as shipped surface, so a new kind of shipped file is covered without anyone adding it to a list. The deliberate consequence is that edits to anything in there, vendored assets and packaged docs among them, now require the full verification round rather than the documentation-only path.
