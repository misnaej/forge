bump: minor
- **A merged change is no longer described as one that reached anybody.** Work that lands on the main branch is not yet available to the people who install this project — under the per-change changelog convention, the version that installers read is written only when a release is assembled, and merging never touches it. Nothing in the rules said so, so an assistant reporting on merged work could call it live or shipped, and could read an update command's "already at the latest version" as confirmation when that line is exactly what being behind looks like. The foundation rules now state the distinction and forbid the stronger claim. Two things are deliberately left where they already live: how releases work, which belongs to each project's own release document, and when to cut one — batching several merges into a single release is the normal shape, and this is explicitly not a chore owed after every merge. What prompts a release is somebody needing to use the work.
